# MetroSched – Phase 1 Design: Synthetic Data & Metro Simulation

> **Synthetic data notice.** Every number in this project is generated by a configurable
> simulation. Nothing here is, or is derived from, Kochi Metro Rail Limited (KMRL)
> operational data, and nothing has been validated against KMRL operations.

## 1. Architecture

```
data/config/metro_config.yaml          single source of truth for all parameters
        │  load_config() – parse, convert "HH:MM" → seconds, validate bounds
        ▼
simulation/
  config.py              loader + validation (ConfigError on bad values)
  exceptions.py          SafetyViolationError hierarchy (hard-constraint rejections)
  train.py               Train dataclass + status state machine + readiness checks
  track.py               TrackSection / Platform / PlatformGroup + audit_occupancy()
  depot.py               stabling berths, exit & reception tracks, induction capacity
  demand_generator.py    demand per 15-min interval + demand → required trains
  scenario_generator.py  normal / peak_demand / disruption days, fleet, induction plan
  metro_environment.py   SimPy model of one operating day + pluggable dispatch policy
  data_generator.py      runs N days, audits safety, writes CSVs
main.py                  CLI: python main.py generate-data --seed 42
```

Layering: `train`, `track` and `depot` know nothing about demand or scheduling;
`metro_environment` composes them; `data_generator` is the only module that writes files.
Later phases plug in without touching the simulation: the FCFS / heuristic / PPO
schedulers are `dispatch_policy` callables, and the Gymnasium environment (Phase 3)
will wrap `MetroEnvironment`'s state and decision points.

## 2. Data flow (per simulated day)

```
master seed ─► SeedSequence ─► day seed ─┬─► demand rng ─► DemandGenerator ─► demand_df (required_trains)
                                          ├─► fleet rng  ─► generate_fleet ─► trains (+ prep delays)
                                          │                  assign_scheduled_inductions(trains, demand_df)
                                          └─► sim rng    ─► MetroEnvironment.run()
                                                               │ logs: inductions, occupancy, delays,
                                                               │       maintenance, snapshots
                                                               ▼
                                                 audit_result()  (abort on any violation)
                                                               ▼
                                                 _aggregate_day() ─► CSV tables
```

## 3. Simulation assumptions

| Topic | Assumption |
|---|---|
| Time | Integer seconds from midnight. SimPy is event-driven (no fixed tick); the dispatch controller re-decides every `decision_interval_s` = 60 s; outputs are aggregated per `interval_s` = 900 s (15 min). |
| Episode | One episode = one operating day: depot opens 04:00, revenue service 05:00–23:00. Days are independent (fleet attributes are redrawn each day). |
| Line | A single line abstracted as a round-trip cycle: `cycle = 2 × (one_way_run_time + terminal_turnaround)` = 2 × (2400 + 300) = 5400 s. Running trains alternate UP/DN legs and pass the depot-station junction for that direction once per leg. |
| Induction route | berth → exit track (1 of 2) → TRANSFER-LINE → DEPOT-JUNCTION → ENTRY-UP/DN → platform dwell → service. Block signalling: the next block is acquired before the current one is released. |
| Withdrawals | Use a separate reception track (no opposing moves on the induction route, so no deadlock). Withdrawn trains need `depot_turnaround_s` before re-induction. |
| Demand → trains | `headway = clip(3600 × capacity × load_factor / demand, min_hw, max_hw)`; `required = clip(ceil(cycle / headway), 1, fleet − reserve)`. E.g. 7 500 pphpd → ≈398 s → 14 trains; off-peak floor (900 s) → 6 trains. |
| Controller | Every 60 s: required trains `induction_lookahead_s` (600 s) ahead vs. trains committed (running + being inducted) → open/cancel induction requests → ask the dispatch policy which **ready** trains to induct. Before service the target is the 05:00 requirement, starting from the first induction window. Surplus trains are withdrawn when demand over the next 30 min stays below the count minus hysteresis. |
| Phase 1 policy | `readiness_order_policy` (earliest readiness first) exists only so the generator can produce an induction history. It is **not** the benchmark; FCFS, heuristic and PPO arrive in Phases 2–4. |
| Randomness | Preparation overruns (exponential), depot faults, odometer-triggered maintenance, repair durations, trip delays, in-service failures, demand noise (lognormal), closures. All from seeded `numpy.random.Generator`s. |

## 4. Hard safety constraints (enforced, never only penalised)

| Constraint | Enforced in | Mechanism |
|---|---|---|
| One train per block / platform | `TrackSection.occupy` | raises `TrackConflictError` |
| Minimum headway after previous train clears | `TrackSection.occupy` | raises `HeadwayViolationError` |
| Closures / possessions | `TrackSection.occupy` | raises `SectionClosedError` |
| Platform capacity | `PlatformGroup.occupy_any` | raises `PlatformCapacityError` |
| Readiness (prep done, no maintenance, in depot, inductable status) | `Train.validate_ready` via `Depot.authorise_induction` | raises `TrainNotReadyError` |
| Induction windows + rolling-hour cap | `Depot.authorise_induction` | raises `InductionCapacityError` |
| Policy may only pick ready trains | `MetroEnvironment._dispatch` | invalid picks rejected and counted (`rejected_actions`) |

The SimPy paths (`reserve`, `acquire_induction_slot`) *wait* until a move is legal and then
call the raising methods, so a correct simulation never raises. `audit_occupancy()` then
re-checks every occupancy log independently; the generator aborts if it finds anything.

## 5. Scenario types

| Type | Changes vs. normal |
|---|---|
| normal | baseline |
| peak_demand | demand ×1.3, more prep delays, trip delays ×1.4, through traffic ×1.2 |
| disruption | prep-delay prob 0.25 (mean 15 min), depot faults 8 %, trip delays ×2.5, 1 exit track closed 30–120 min, 2 shared-section blocks, 1 platform closure, +30 s headway everywhere, induction capacity ×0.75 |

## 6. Output tables (`data/generated/`)

| File | Grain | Key columns |
|---|---|---|
| scenarios.csv | day | scenario_type, weekday, seed, all scenario parameters, closures |
| passenger_demand.csv | day × 15 min | period, is_peak, demand_pphpd, service_headway_s, required_trains |
| train_readiness.csv | day × train | depot_location, readiness_time_s, min_prep_time_s, prep_delay_s, maintenance_required, induction_priority, scheduled_induction_time_s |
| train_availability.csv | day × 15 min × train | status, location |
| fleet_status_by_interval.csv | day × 15 min | n_available … n_delayed, required_trains, in_service, service_shortfall |
| induction_windows.csv | day × window | start/end, max_inductions, inductions_used, max_inductions_per_hour |
| track_availability.csv | day × 15 min × section | occupied_s, closed_s, available_s, utilization, train_entries, is_available |
| platform_occupancy.csv | day × 15 min × platform | occupied_s, closed_s, utilization, is_open |
| maintenance_events.csv | event | event_type (planned / depot_fault / in_service_failure), start/end |
| operational_delays.csv | event | delay_type (preparation / in_service / junction_congestion / induction_track_wait / reception_wait), delay_s |
| induction_history.csv | induction | request, needed-by, authorised, depot exit, mainline entry, service start times; exit track, entry point, platform; capacity_wait_s, track_wait_s, induction_delay_s, schedule_deviation_s |
| track_occupancy_log.csv | occupancy | raw block occupation intervals (for Gantt charts and audits) |
| dataset_manifest.json | – | seed, config hash, scenario counts, row counts, safety_violations (= 0) |

`induction_delay_s` = how late a train entered service versus when it was needed
(`needed_by_time_s`); `track_wait_s` = time spent waiting for blocks/platforms beyond the
unimpeded route time.

## 7. Implementation status

All eight phases are implemented; see `docs/TECHNICAL_REPORT.md` for Phases 2–8.

Changes made to the simulation in later phases, so that schedulers can be compared fairly:
* **External control** (`control="external"`): FCFS, heuristic and PPO request inductions
  through `MetroEnvironment.apply_induction`, which atomically checks readiness and capacity.
* **Common random numbers**: each train has its own random stream for trip delays,
  failures and repairs, so all schedulers face identical random events on a given seed.
* **Wear-dependent failures**: in-service failure probability scales with
  km since maintenance (0.5× … ~1.6×), so the choice of train matters.
* A per-minute service monitor (required vs in service, queued trains) feeds the metrics.
