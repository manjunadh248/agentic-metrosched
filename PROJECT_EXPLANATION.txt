1. PROJECT SUMMARY (ABSTRACT)
===============================================================================

MetroSched is an AI system that decides how to release trains from a metro
depot onto the main line during an operating day. This step is called "train
induction". Each time, the system must decide WHICH train to send, WHEN to send
it, and through WHICH entry point. The goal is to have enough trains in service
to carry the passenger demand while never breaking any safety rule.

The project has three layers:

  (a) A SIMULATION of a metro depot and line (built with SimPy). It generates
      the synthetic dataset and acts as the environment where every decision
      is tested.

  (b) Three SCHEDULERS that make the minute-by-minute induction decisions:
        - FCFS baseline (first-come-first-served, no intelligence)
        - Rule-based heuristic (hand-written expert rules)
        - PPO agent (a Reinforcement Learning agent trained on simulated days)

  (c) An AGENTIC AI ASSISTANT (an LLM agent built on Claude). It takes an
      operator's question in plain English, plans which experiments to run,
      runs them on the simulator and schedulers through tools, checks the
      results, and writes a recommendation backed by the simulated numbers.

On 120 operating days that were never used in training, the PPO agent cut the
average induction delay by 75% and the service shortfall by 70% compared with
the FCFS baseline. It also achieved the lowest train waiting time of the three
schedulers. The hand-written heuristic is still slightly better on some metrics.
All schedulers recorded zero safety violations, because safety is enforced by
the simulator, not learned.


===============================================================================
2. THE PROBLEM WE SOLVE
===============================================================================

Every morning a metro depot holds about 25 trainsets. Before and during service
the control room must "induct" trains: move them from the depot, through exit
tracks and a shared transfer line, onto the main line, where they start
carrying passengers.

This is hard because:

  * Passenger demand changes through the day: a morning peak (~08:45), a small
    afternoon peak (~13:30) and an evening peak (~18:15).
  * A train sent too LATE leaves passengers without enough service.
  * Trains sent too EARLY, or several at once, queue on the single transfer
    line, waste train-hours and use up the limited induction capacity that is
    needed later for the evening peak.
  * Trains are not all equal. A train with high kilometres since maintenance
    is more likely to fail in service, so WHICH train is sent matters.
  * Things go wrong: preparation overruns, depot faults, track closures,
    platform closures, extra safety headway, reduced induction capacity.
  * Every movement must respect strict safety rules (section 9).

So the problem is sequential decision-making under uncertainty, with several
objectives and hard constraints. That is exactly the kind of problem AI agents
are suited for.


===============================================================================
3. WHY AI IS NEEDED
===============================================================================

  * A simple rule such as FCFS only reacts to the situation right now. It does
    not anticipate demand, so trains arrive late at every peak.
  * Hand-written rules (the heuristic) work, but an expert must write and tune
    them, and they do not adapt automatically.
  * A Reinforcement Learning agent LEARNS a decision policy from thousands of
    simulated days by trial and error, guided by a reward signal.
  * Operators also have "what-if" questions ("platform 2 is closed tomorrow
    morning, what should we do?"). Answering them means building a scenario,
    running several schedulers, comparing them and explaining the result. An
    LLM agent can do this whole multi-step job on its own, in natural language.


===============================================================================
4. WHERE AI IS USED
===============================================================================

There are TWO AI agents, working at different levels (a hierarchical
multi-agent system), plus a rule-based safety layer.

  +-------+-----------------------+------------------------+-------------------+
  | Level | Agent                 | Type of AI             | What it decides   |
  +-------+-----------------------+------------------------+-------------------+
  |   1   | MetroOpsAgent         | Agentic AI +           | what to test,     |
  |       | (agentic/agent.py)    | Generative AI (LLM,    | what to recommend,|
  |       |                       | Claude, tool use)      | writes the answer |
  +-------+-----------------------+------------------------+-------------------+
  |   2   | PPO scheduler         | Reinforcement Learning | which train goes, |
  |       | (reinforcement_       | (deep RL, neural       | when, and through |
  |       |  learning/, models/)  | network policy)        | which entry point |
  +-------+-----------------------+------------------------+-------------------+
  |   3   | Simulator safety      | Rule-based guard       | whether an action |
  |       | layer (simulation/)   | (not AI)               | is allowed at all |
  +-------+-----------------------+------------------------+-------------------+

4.1 AGENTIC AI
  An "agent" perceives its environment, decides by itself, acts, and pursues a
  goal. Both of our agents do this:

    LLM agent (MetroOpsAgent):
      perceive : reads the operator question and the tool results
      plan     : decides which tool to call next
      act      : calls tools (create a what-if day, run schedulers, ...)
      observe  : receives KPIs, demand profile, fleet state, induction logs
      reflect  : tests another variant if the result is close or surprising
      answer   : writes a recommendation
      memory   : keeps the conversation, so follow-up questions work

    PPO agent:
      perceive : 78 numbers describing the depot and line every 60 seconds
      decide   : picks one of 13 actions (wait, or send train k via entry e)
      act      : the decision is applied in the simulator
      learn    : improved its policy from reward over 400,000 training steps

4.2 GENERATIVE AI
  The LLM agent (Claude, from Anthropic) is generative AI. It understands free
  text and GENERATES the final answer in natural language: situation, what it
  tested, a results table, a recommendation and caveats. It is "grounded": it
  may only quote numbers that came from tool results, never invent them.

  Note: the dataset is called "synthetic", but it is NOT produced by
  generative AI. It comes from a rule-based random simulation.

4.3 REINFORCEMENT LEARNING / DEEP LEARNING
  The PPO agent is a neural network (2 hidden layers of 128 units) trained with
  Proximal Policy Optimization (MaskablePPO), after a behaviour-cloning warm
  start (supervised learning that imitates the heuristic). It is built with
  PyTorch, Stable-Baselines3, sb3-contrib and Gymnasium.

5.2 Physical layout that is simulated

   DEPOT (10 stabling lines x 3 berths, 25 trains)
      |
      +-- EXIT-1 (1 train at a time, headway 120 s) --+
      |                                               |
      +-- EXIT-2 (1 train at a time, headway 120 s) --+
                                                      |
                              TRANSFER-LINE (single track, headway 120 s)
                                                      |
                              DEPOT-JUNCTION (headway 90 s)
                                                      |
                        +-----------------------------+---------------------+
                        |                                                   |
                  ENTRY-UP (headway 120 s)                     ENTRY-DN (headway 120 s)
                        |      (through trains also use these junctions)    |
                        +---------------- PLATFORMS PF-1, PF-2 -------------+
                                               |
                                    MAIN LINE (revenue service)
                                    round trip = 2 x (2400 + 300) s = 90 min

   Trains returning to the depot use a separate RECEPTION track, so the
   induction route never has opposing moves (no deadlock).

5.3 The decision cycle (same for all schedulers)

   every 60 simulated seconds:
       for up to 3 times:
           decision = scheduler.decide(environment)    # train + entry, or wait
           if decision is "wait": stop
           ok = environment.apply_induction(decision)  # safety + capacity check
           if not ok: stop (the request is rejected and logged)
   at the end of the day:
       compute metrics from the logs
       run an independent safety audit on all occupancy records

5.4 The agentic loop (LLM agent)

   messages = [operator question]
   repeat (at most 15 turns):
       response = Claude(system prompt, tools, messages)
       if response has no tool calls:   -> return final answer
       for each tool call: run the tool on the simulator
       send ALL tool results back in one message
       (Claude now decides: enough evidence, or another experiment?)

  Command: python main.py generate-data --seed 42
  The simulation runs 30 operating days with master seed 42 and writes CSV
  files to data/generated/. The same seed always gives exactly the same data.
  A safety audit runs on the generated data: 0 violations.

  Day mix in the 30-day dataset: 17 normal, 5 peak-demand, 8 disruption.
  Fleet: 25 trainsets (TS01 ... TS25).

7.3 How the data is used
  * The dataset is for analysis, the dashboard's Operations overview page and
    documentation.
  * The RL agent does NOT learn from these CSV files. It learns by
    interacting with the simulator, which creates a new random day for every
    training episode (seeds 0 to 999,999).
  * Validation days use seeds from 500,000,000 and final test days use seeds
    from 900,000,000. The three seed ranges never overlap, so the agent is
    always tested on days it has never seen.

7.4 Key generation parameters (data/config/metro_config.yaml)
  * Operating day: depot opens 04:00, service 05:00-23:00, decision every 60 s.
  * Train capacity 975 passengers, target load factor 0.85.
  * Preparation time 20-40 min per train, staggered by 2 min.
  * km since maintenance: 0-6000; above 5500 km the train needs maintenance.
  * Priority levels 1 (best, low km) to 5 (worst, high km).
  * Demand: base 2600 pphpd + Gaussian peaks (morning x1.9, afternoon x0.55,
    evening x1.7), weekday factors (Sat 0.85, Sun 0.70), 6% random noise.
  * Required trains = demand converted to headway (5 to 15 min) and then to
    trains needed for a 90-min round trip, plus 2 reserve trains.
  * Random operational delays (4% of trips, mean 150 s), in-service failure
    probability 0.4% per round trip (rises with km since maintenance), repair
    1-4 hours.

8. THE SIMULATION (DIGITAL TWIN)
===============================================================================

  * Built with SimPy, a discrete-event simulation library for Python.
  * One episode = one operating day.
  * Each train is a state machine:
        Available -> Inducted -> Running -> (Delayed) -> back to depot
        Maintenance (cannot be inducted)
  * An inducted train moves: exit track -> transfer line -> depot junction ->
    entry point -> platform (60 s dwell) -> service.
  * Running service trains pass the entry junctions every half-cycle, so main
    line traffic competes with inductions (realistic congestion).
  * When trains in service exceed the need for the next 30 min by more than 1,
    surplus trains are withdrawn to the depot (with hysteresis).
  * Common random numbers: each train has its own random stream. On the same
    seed, every scheduler faces EXACTLY the same faults, delays and failures.
    This makes the comparison fair.
  * Everything is logged: inductions, occupancy, closures, delays,
    maintenance and a per-minute monitor (required vs in service).


===============================================================================
9. SAFETY RULES (HARD CONSTRAINTS)
===============================================================================

These are ENFORCED by the simulator. A request that breaks one is rejected or
made to wait. It is never just "penalised". This holds for every scheduler and
for every tool the LLM agent calls.

  1. Single occupancy: every track block and platform holds at most 1 train.
  2. Minimum safety headway after a train clears a section (90-120 s, plus
     30 s on disruption days).
  3. Closures: no train may enter a closed exit track, section or platform.
  4. Readiness: only trains that have finished preparation, need no
     maintenance and are in the depot can be inducted.
  5. Induction capacity: max 8 inductions per rolling hour, and only inside
     the induction windows (W1 04:15-10:30 max 22, W2 10:30-15:30 max 10,
     W3 15:30-20:30 max 16, W4 20:30-22:30 max 4).
  6. Platform clearance: 60 s after a train leaves a platform.

After every simulated day an INDEPENDENT AUDIT re-checks all occupancy records
against these rules. Result: 0 violations for all schedulers on all evaluated
days.

Design principle: the AI decides, but it cannot override safety. The PPO
agent also uses action masking, so impossible actions are never even chosen.


===============================================================================
10. THE THREE SCHEDULERS
===============================================================================

10.1 FCFS baseline (scheduling/baseline_fcfs.py)
  When the number of committed trains is below what is required RIGHT NOW,
  send the earliest-ready train. The environment picks the exit track and
  entry point. No look-ahead, no awareness of congestion or train health.

10.2 Rule-based heuristic (scheduling/heuristic_scheduler.py)
  1. Anticipate: target = maximum required trains over the next 12 minutes.
  2. Avoid bunching: if a train is already queued on the induction route,
     hold (unless service is short right now).
  3. Prefer healthy trains: lowest induction priority (lowest km), then
     earliest ready.
  4. Choose the entry point that will be clear soonest when the train arrives.

10.3 PPO agent (scheduling/rl_scheduler.py + reinforcement_learning/)
  A trained neural network looks at the current state and outputs a
  probability for each of 13 actions. A safety shield removes infeasible
  actions, and an action is drawn from the remaining probabilities. For every
  induction it explains itself: the probability of the chosen action, the
  best alternative, and the features of the chosen train.


===============================================================================
11. THE REINFORCEMENT-LEARNING AGENT IN DETAIL
===============================================================================

11.1 Observation (what the agent "sees") - 78 numbers, every 60 s
  * time of day
  * required trains now, +10, +20, +30, +60 min
  * demand now and +30 min
  * trains in service, committed, being inducted, queued, withdrawing, delayed
  * current and 30-min-ahead service gap
  * remaining induction capacity (rolling hour, current window), inductions in
    the last hour, time since last induction
  * ready / pending / maintenance counts
  * for each of 7 track sections: occupancy, time to clear, closure, queue
  * for 6 candidate trains: present, priority, km since maintenance, time
    since ready

11.2 Action - Discrete(13)
  0          = wait
  1 + 2k + e = induct candidate k (k = 0..5) via entry point e (UP or DN)
  The 6 candidates = the 3 best-priority trains + the 3 earliest-ready trains.
  This covers "which train", "which entry" and "wait for a better moment".

11.3 Action masking
  Infeasible actions (empty candidate slot, no capacity left) are masked out
  during training (MaskablePPO) and at deployment (safety shield).

11.4 Reward function (reinforcement_learning/reward_function.py)
  Computed every 60 s. Rates are per train-minute, events per occurrence.
  +------------------------------------------------+--------+------+
  | Term                                           | Weight | Sign |
  +------------------------------------------------+--------+------+
  | Service shortfall (required - in service)      |  0.30  |  -   |
  | Missed induction opportunity (slot expired)    |  1.00  |  -   |
  | Useful induction (fills a service gap)         |  0.50  |  +   |
  | In service within [required, required+1]       |  0.05  |  +   |
  | Unnecessary deployment (above need + 1)        |  0.03  |  -   |
  | Trains queued on the induction route           |  0.05  |  -   |
  | New queueing event (track contention)          |  0.10  |  -   |
  | Delayed trains in service                      |  0.02  |  -   |
  | In-service failure (worn train inducted)       |  1.00  |  -   |
  | Rejected (invalid) action                      |  0.10  |  -   |
  +------------------------------------------------+--------+------+
  Priority order: serve demand first, then avoid missed slots and failures,
  then waiting and contention, then waste.

11.5 Training procedure
  Step 1 - Behaviour cloning (supervised warm start, pretrain.py):
           the network imitates the heuristic on 60 training days
           (68,596 decisions, 40 epochs). Action accuracy: 96.9%.
  Step 2 - MaskablePPO fine-tuning (train_agent.py):
           400,000 steps (about 350 simulated days), 2 parallel environments,
           about 32 minutes on a 2-core CPU.
           Hyperparameters: MLP 128-128, learning rate 3e-5, gamma 0.995,
           GAE lambda 0.95, clip 0.1, 5 epochs, batch 256, n_steps 2048,
           target KL 0.015.
           Training day mix: normal 45%, peak 30%, disruption 25%.
  Step 3 - Model selection: every 20,000 steps the model is tested on 12
           fixed validation days. The model with the best validation return
           is kept (models/ppo_metrosched.zip).
           Validation return: PPO 12.7, FCFS -27.3, heuristic +17.3.

11.6 What did not work (reported honestly)
  * Plain PPO from a random start did not learn within the CPU budget
    (validation return stayed around -460). Because 12 of 13 actions are
    "induct", a random policy over-inducts, and the penalty arrives hours
    later. That is why behaviour cloning was added.
  * Choosing the single most probable action (argmax) delayed inductions,
    because after imitation "wait" is the most probable action at almost
    every tick. Seeded sampling worked much better (+12.4 vs -4.5).


===============================================================================
12. THE AGENTIC AI LAYER (LLM AGENT) IN DETAIL
===============================================================================

12.1 Purpose
  The schedulers answer one narrow question: which train next? The LLM agent
  answers the operator's broader, open questions, such as:
    - "Festival tomorrow, demand +25%, platform 2 closed 08:00-09:30. What
       should we do and what are the first inductions?"
    - "Exit track 1 closed 17:00-18:30. How much does it hurt the evening
       peak?"
    - "Only 21 trainsets today. Is the RL agent still better than FCFS?"
    - "Overall, how does the RL agent compare with the heuristic?"

12.2 The model
  Claude (Anthropic), default model id "claude-opus-5-5"; Sonnet or Haiku can
  be chosen instead. Called through the official Anthropic Python SDK with tool
  use. Server-side fallback is enabled for safety-classifier declines.

12.3 The 8 tools (agentic/tools.py)
  +----------------------+-----------------------------------------------------+
  | Tool                 | What it does                                        |
  +----------------------+-----------------------------------------------------+
  | get_system_overview  | infrastructure, fleet, headways, windows, available |
  |                      | schedulers, valid section ids                       |
  | get_saved_evaluation | stored benchmark over 120 unseen days (overall or   |
  |                      | per scenario type), % vs FCFS                       |
  | create_scenario      | builds a WHAT-IF day: type, seed, demand multiplier,|
  |                      | fleet size, extra headway, extra closures (HH:MM)   |
  | get_demand_profile   | hourly demand and required trains, peak hours       |
  | get_fleet_status     | each train's readiness, priority, km, maintenance   |
  | run_scheduler        | simulates the full day with FCFS/Heuristic/PPO,     |
  |                      | returns KPIs + safety audit                         |
  | compare_schedulers   | runs several schedulers on IDENTICAL conditions,    |
  |                      | side-by-side table + best per metric                |
  | get_induction_plan   | the sequence of inductions with times, tracks,      |
  |                      | waits and the scheduler's own explanation           |
  +----------------------+-----------------------------------------------------+
  Every tool has a JSON schema. Inputs are validated (e.g. demand 0.5-2.0,
  fleet 15-30, valid section ids, end after start, and the agent may not close
  every exit track at the same time). Errors are sent back to the model as
  tool errors so it can correct itself. Simulation runs are cached.

12.4 System prompt (rules given to the agent)
  * Turn the situation into a concrete what-if day.
  * Gather evidence with simulations, and reflect: if a result is close or
    surprising, test another variant before concluding.
  * Every number must come from a tool result. Never invent figures.
  * Report the safety audit; never suggest bypassing a safety rule.
  * State that the data is synthetic.
  * Answer format: Situation / What I tested / Results (table) /
    Recommendation / Caveats.

12.5 Example trace (real run, offline mode)
  Question: "Festival tomorrow, demand +25%, platform 2 closed 8:00-9:30"
    1  reason   plan the experiments
    2  act      create_scenario(peak_demand, demand x1.25, close PF-2 08:00-09:30)
    3  observe  scenario S1 created
    4  act      get_demand_profile(S1)
    5  observe  peak need 18 trains around 07:00-08:00 and 17:00
    6  act      compare_schedulers(S1)
    7  observe  FCFS / Heuristic / PPO table
    8  reflect  lowest service shortfall -> Heuristic (0.52 vs FCFS 3.92 train-h)
    9  act      get_induction_plan(S1, Heuristic)
    10 observe  first 6 inductions
    11 answer   table + recommendation, 0 safety violations

12.6 Two modes
  +-------------------------+------------------------+------------------------+
  |                         | LLM agent              | Offline planner        |
  |                         | (MetroOpsAgent)        | (OfflineAgent)         |
  +-------------------------+------------------------+------------------------+
  | Understands free text   | yes (Claude)           | keywords / regex only  |
  | Chooses its own steps   | yes                    | fixed plan             |
  | Generative AI           | yes                    | no (template answer)   |
  | Needs API key / network | yes                    | no                     |
  | Same tools, same safety | yes                    | yes                    |
  +-------------------------+------------------------+------------------------+
  The offline planner is a backup for demos without internet. The agentic AI
  and generative AI part of the project is the LLM mode.

13. EVALUATION METHOD AND RESULTS
===============================================================================

13.1 Method
  * 120 UNSEEN days (seeds 900,000,000 to 900,000,119), 40 of each scenario
    type, never used in training or validation.
  * Every scheduler runs every day under identical conditions.
  * Metrics are computed from the simulation logs, not hard-coded.
  * Improvement = (FCFS - X) / FCFS x 100 for lower-is-better metrics.
  * Statistics: mean, std, 95% confidence intervals, paired bootstrap, exact
    sign tests (results/evaluation/summary.csv).

13.2 Metric definitions
  * Induction delay: time from when a "demand slot" opens (required trains
    rises) until a train fills it.
  * Missed opportunity: a slot that closed before any train filled it.
  * Service shortfall: sum of (required - in service) over the day, in
    train-hours.
  * Demand coverage: share of passenger demand that had enough capacity.
  * Induction conflict: an induction that had to queue behind another train
    (resolved safely, NOT a safety violation).
  * Waiting time: capacity wait + track wait per induction.
  * Unnecessary deployment: train-hours above need + 1.

13.3 Results (mean +/- std over 120 unseen days)
  +-----------------------------------+--------------+--------------+--------------+----------+
  | Metric                            | FCFS         | Heuristic    | PPO agent    | PPO vs   |
  |                                   |              |              |              | FCFS     |
  +-----------------------------------+--------------+--------------+--------------+----------+
  | Induction conflicts (/day)        | 11.99 +-3.88 | 11.45 +-3.41 | 12.79 +-4.12 |  -6.7%   |
  | Avg induction delay (min)         |  5.90 +-3.71 |  1.21 +-3.21 |  1.45 +-2.70 | +75.4%   |
  | Avg train waiting time (min)      |  4.61 +-5.84 |  4.05 +-5.44 |  3.89 +-5.25 | +15.7%   |
  | Passenger demand coverage (%)     | 98.69 +-1.16 | 99.67 +-0.93 | 99.57 +-1.07 |  +0.9%   |
  | Missed opportunities (/day)       |  0.68 +-1.18 |  0.23 +-0.73 |  0.38 +-0.90 | +43.2%   |
  | Service shortfall (train-h/day)   |  3.05 +-1.93 |  0.65 +-1.57 |  0.93 +-1.76 | +69.6%   |
  | Unnecessary deployment (tr-h/day) |  6.41 +-2.25 |  6.74 +-2.32 |  6.88 +-2.48 |  -7.3%   |

  +-----------------------------------+--------------+--------------+--------------+----------+
  (+ = better than FCFS, - = worse than FCFS)

13.4 Interpretation
  * PPO vs FCFS: clearly better on every service metric (delay -75%,
    shortfall -70%, missed -43%, waiting -16%), all statistically significant.
    The main reason is anticipation: it inducts before demand rises.
  * Costs of PPO: slightly more train-hours (+7%) and slightly more queueing
    conflicts (+7%).
  * PPO vs heuristic: PPO has the LOWEST waiting time of all three, but the
    heuristic is slightly better on delay, shortfall and missed slots. Within
    this CPU budget, PPO fine-tuning did not improve on its imitation warm
    start. The heuristic is a strong fallback, and the LLM agent recommends
    it when the simulation shows it is better.
  * Safety: 0 violations on all 360 evaluated scheduler-days.

===============================================================================
18. LIMITATIONS
===============================================================================

  * Synthetic data and a simplified single-line metro. The numbers are
    illustrative, not KMRL's.
  * The PPO model is tied to the track layout it was trained on (the number of
    sections sets the observation size). A different layout needs retraining.
  * PPO did not beat the hand-written heuristic within the CPU training budget.
  * Demand does not react to service quality. Crew rostering, energy use and
    shunting inside the depot are not modelled.
  * Only 12 validation days were used for model selection.
  * The LLM agent needs internet and an API key, and each question costs a
    small amount. Its recommendations are only as good as the simulation.

20. LIKELY VIVA QUESTIONS AND ANSWERS
===============================================================================

Q: Where is agentic AI used in your project?
A: In two places. (1) The LLM agent (agentic/agent.py) takes a question, plans,
   calls tools on the simulator, observes results, reflects and answers on its
   own. (2) The PPO agent is an autonomous RL agent that perceives the depot
   state every minute and decides which train to induct. Together they form a
   hierarchical multi-agent system.

Q: Where is generative AI used?
A: The LLM agent uses Claude, a large language model. It generates the plan of
   experiments and the final natural-language recommendation. The dataset is
   NOT made by generative AI; it comes from a rule-based simulation.

Q: What dataset did you use?
A: A synthetic dataset from our own SimPy simulation: 30 days, 25 trains, 12
   CSV files, about 90,000 rows, seed 42. It is not real KMRL data. The RL
   agent learns by interacting with the simulator, not from the CSVs.

Q: Why synthetic data?
A: Real depot operational data is not publicly available. A simulation also
   lets us create unlimited training days, rare disruptions and fair
   comparisons (identical conditions for every scheduler).

Q: What is PPO?
A: Proximal Policy Optimization, a policy-gradient RL algorithm. It improves
   the policy in small, "clipped" steps so learning stays stable. We use
   MaskablePPO, which ignores invalid actions.

Q: Why behaviour cloning before PPO?
A: PPO from scratch did not learn within our CPU budget: a random policy
   over-inducts trains and the penalty comes hours later. Imitating the
   heuristic first gives PPO a sensible starting point (96.9% accuracy).

Q: How do you guarantee safety?
A: Safety is enforced in the simulator, not learned. Unsafe requests are
   rejected or made to wait, and an independent audit re-checks every day.
   Result: 0 violations. The LLM agent can only call tools that go through
   the same checks.

Q: Is your RL agent better than the rules?
A: Better than FCFS on every service metric (-75% delay, -70% shortfall). It
   has the lowest waiting time of all three, but the hand-written heuristic is
   slightly better on delay and shortfall. We report this honestly, and the
   LLM agent recommends whichever scheduler the simulation shows is best.

Q: How does the LLM agent avoid making up numbers?
A: It is grounded. The system prompt requires every number to come from a
   tool result, and all the tools return real simulation results.

Q: What if there is no internet in the demo?
A: Use --offline. It uses the same tools and a fixed rule-based plan, but it is
   not generative AI.

Q: What is the difference between a tool and an agent?
A: A tool is a function that does one job when called (e.g. run a
   simulation). An agent decides by itself which tools to call, in which
   order, and when it has enough information to stop.

Q: How is the comparison fair?
A: All schedulers run on the same 120 unseen days with the same demand,
   faults and random streams (common random numbers), through the same
   decision interface (every 60 s, up to 3 inductions).

21. GLOSSARY
===============================================================================

  Induction        Releasing a train from the depot into passenger service.
  Depot            Yard where trains are parked, prepared and maintained.
  Headway          Minimum time gap between two trains on the same section.
  Section/block    Piece of track that may hold only one train at a time.
  pphpd            Passengers per hour per direction (demand unit).
  Scenario         One simulated operating day (normal, peak, disruption).
  Seed             Number that fixes the random generator: same seed = same day.
  SimPy            Python library for discrete-event simulation.
  Digital twin     Software model that behaves like the real system.
  Agent            Software that perceives, decides and acts toward a goal.
  Agentic AI       AI that plans and acts autonomously, using tools, over
                   multiple steps.
  Generative AI    AI that generates new content (text, images, ...), e.g. an
                   LLM.
  LLM              Large Language Model (here: Claude by Anthropic).
  Tool use         An LLM calling external functions with JSON arguments.
  RL               Reinforcement Learning: learning by trial and error from a
                   reward.
  PPO              Proximal Policy Optimization (RL algorithm).
  Action masking   Hiding invalid actions from the RL agent.
  Behaviour        Supervised learning that copies an expert's decisions.
   cloning
  Reward           Number telling the RL agent how good its last step was.
  Policy           The agent's decision rule (here: a neural network).
  FCFS             First-Come-First-Served.
  Heuristic        Hand-written rules of thumb.
  KPI              Key Performance Indicator.
